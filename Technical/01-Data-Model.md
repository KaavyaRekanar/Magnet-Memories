# Data Model

**Project:** Magnet Memories
**Document:** Data Model
**Version:** 1.0
**Status:** Draft

---

# Purpose

This document defines the domain and persistence models for Magnet Memories Version 1.

It specifies:

* core entities;
* relationships;
* identifiers;
* constraints;
* Room database structure;
* media representation;
* Journey ordering;
* Live Photo pairing;
* import lifecycle state;
* playback resume state;
* deletion behaviour;
* migration principles.

The data model must support the complete offline experience while remaining understandable, portable and extensible.

---

# Data-Modelling Principles

The data model should follow these principles.

## Model the Family Journal

Domain terminology should describe the product rather than Android implementation details.

Use:

* Journey;
* Moment;
* Memory Card;
* Still Photo;
* Live Photo.

Avoid exposing terms such as:

* database row;
* media payload;
* file entity;
* slideshow item.

---

## Separate Durable Content From Presentation

The database should store content that must survive application restarts.

It should not store every temporary or presentational playback element.

For example:

* Journey metadata is persisted.
* Imported photo Moments are persisted.
* The Title Page may be generated at runtime.
* The Closing Page may be generated at runtime.
* Temporary animation state is not persisted.

---

## Strong Types Over Arbitrary Payloads

Moment types should be explicit and validated.

Avoid using a single unstructured JSON payload for every Moment type.

Strong models improve:

* validation;
* migrations;
* testing;
* reliability;
* readability.

---

## Files Remain Outside the Database

Room should store metadata and app-managed relative file references.

It must not store:

* image byte arrays;
* video byte arrays;
* thumbnails as blobs;
* original source media.

---

## Original Media Is Never Owned by the Database

Source files on the external hard drive remain outside application control.

The database describes only imported local copies and their relationship to the source import.

Deleting database records must never delete or modify original archive files.

---

## Offline Operation Is Authoritative

The local database and app-managed media files form the working journal.

Playback must not depend on:

* external folder permissions;
* temporary content URIs;
* internet services;
* cloud identifiers.

---

Journal

    ├── Stored Moments
    │   ├── Still Photo
    │   └── Live Photo

    ├── NFC Slug

Version 1 contains one implicit Journal with many Journeys.

A dedicated Journal entity is not required in Version 1.

# Domain Types

The domain layer should use strongly typed identifiers and values.

Examples below are conceptual Kotlin models. Exact implementation may use inline value classes, type aliases or validated data classes.

---

## JourneyId

A stable internal identifier.

```kotlin
@JvmInline
value class JourneyId(val value: String)
```

Requirements:

* generated by the application;
* globally unique within the local journal;
* immutable;
* not derived from the Journey title;
* not exposed on NFC tags.

Recommended format:

* UUID;
* ULID;
* another well-supported stable identifier.

UUID is the simplest Version 1 choice.

---

## MomentId

A stable internal identifier for one persisted Moment.

```kotlin
@JvmInline
value class MomentId(val value: String)
```

Requirements:

* unique across the local database;
* immutable;
* generated before final local media filenames are created;
* used to derive app-managed media references where practical.

---

## JourneySlug

A validated public identifier written to an NFC tag.

```kotlin
@JvmInline
value class JourneySlug private constructor(
    val value: String
)
```

Example:

```text
new-york-2026
```

Used in:

```text
magnetmemories://journey/new-york-2026
```

Slug rules:

* lowercase ASCII letters;
* numbers;
* single hyphens between words;
* no spaces;
* no leading or trailing hyphen;
* no consecutive hyphens;
* recommended maximum length: 64 characters;
* unique within the journal;
* stable after a magnet has been programmed.

Suggested validation expression:

```regex
^[a-z0-9]+(?:-[a-z0-9]+)*$
```

Changing a slug after programming a tag may invalidate the existing magnet.

The Workshop must warn the owner before allowing such a change.

# Journey Domain Model

A Journey represents one family travel experience.

Conceptual model:

```kotlin
data class Journey(
    val id: JourneyId,
    val slug: JourneySlug,
    val title: String,
    val location: String?,
    val startDate: LocalDate?,
    val endDate: LocalDate?,
    val story: String,
    val favouriteQuote: String?,
    val coverMomentId: MomentId?,
    val accentKey: String?,
    val sourceFolderName: String?,
    val createdAt: Instant,
    val updatedAt: Instant
)
```

---

## Journey Field Rules

### `id`

Required.

Stable internal identifier.

---

### `slug`

Required.

Unique.

Used for NFC Journey resolution.

---

### `title`

Required.

User-facing Journey title.

Examples:

* New York
* Summer in Sweden
* Japan

Rules:

* trim surrounding whitespace;
* must contain at least one visible character;
* recommended maximum length: 100 characters;
* preserve the owner's original capitalisation.

---

### `location`

Optional.

Examples:

* New York City, USA
* Stockholm and Gävle, Sweden
* Tokyo, Kyoto and Osaka

Recommended maximum length:

```text
200 characters
```

---

### `startDate`

Optional.

Stored as an ISO local calendar date.

---

### `endDate`

Optional.

Must not precede `startDate` when both are present.

A Journey may have:

* both dates;
* only a start date;
* no dates.

---

### `story`

Required as a field, but may initially contain an empty string while a Journey is being drafted.

Before a Journey is marked ready for public playback, the application should encourage a non-empty Memory Card story.

Recommended target:

```text
50–140 words
```

A hard technical maximum should be generous enough to preserve authored content.

Suggested maximum:

```text
5,000 characters
```

The UI may impose a lower recommended limit without truncating stored content.

---

### `favouriteQuote`

Optional.

Suggested maximum:

```text
300 characters
```

---

### `coverMomentId`

Optional during import or draft creation.

Must reference a Moment belonging to the same Journey.

Before public playback, a cover should be selected automatically or manually.

---

### `accentKey`

Optional reference to a curated visual accent.

It should not store an arbitrary executable theme or colour payload.

Example values:

```text
muted-crimson
moss
deep-blue
amber
```

---

### `sourceFolderName`

Optional informational value.

May be used to help identify duplicate imports.

It must not be treated as an active file-system path.

---

### `createdAt`

Required.

Application-controlled timestamp.

---

### `updatedAt`

Required.

Updated whenever Journey metadata or ordered content changes.

---

# Memory Card Representation

The Memory Card belongs to Journey metadata rather than being a separate mandatory database entity in Version 1.

The persisted content consists of:

* Journey title;
* location;
* dates;
* story;
* favourite quote;
* cover Moment reference.

The playback sequence builder generates a `MemoryCardMoment` at runtime.

Conceptual playback model:

```kotlin
data class MemoryCardMoment(
    override val id: PlaybackMomentId,
    override val journeyId: JourneyId,
    val title: String,
    val location: String?,
    val startDate: LocalDate?,
    val endDate: LocalDate?,
    val story: String,
    val favouriteQuote: String?,
    val cover: LocalImageReference?
) : PlaybackMoment
```

This avoids duplicating Journey metadata in another persisted row.

A dedicated Memory Card table may be introduced later only if:

* Journeys support multiple story pages;
* version history is required;
* collaborative editing is introduced;
* multiple Memory Cards belong to one Journey.

---

# Moment Model

A stored Moment is one durable memory imported into a Journey.

Version 1 supports:

* Still Photo;
* Live Photo.

Runtime-only Moment types include:

* Title Page;
* Memory Card;
* Closing Page.

# Local Media References

The domain should not expose raw `File` instances or absolute paths unnecessarily.

Conceptual type:

```kotlin
@JvmInline
value class LocalMediaReference(
    val relativePath: String
)
```

Examples:

```text
journeys/{journeyId}/stills/{momentId}.jpg
journeys/{journeyId}/motion/{momentId}.mp4
journeys/{journeyId}/thumbnails/{momentId}.webp
```

Requirements:

* relative to an application-controlled media root;
* validated to prevent path traversal;
* never supplied directly by user-authored metadata;
* resolved through `JourneyStorage`;
* portable if the app-managed root changes.

Separate semantic wrappers may be used:

```kotlin
value class LocalImageReference(...)
value class LocalMotionReference(...)
```

# Source Fingerprints

Fingerprints help identify duplicate imports.

A source fingerprint may combine:

* file size;
* normalised original filename;
* capture timestamp;
* cryptographic or partial content hash.

A full cryptographic hash is reliable but may be expensive for large media.

The import design may use staged duplicate detection:

1. quick candidate detection using metadata;
2. stronger hash verification where required.

Fingerprints must not be used as primary entity identifiers.

# Playback Moment Model

The Memory Player consumes a generated sequence.

```kotlin
sealed interface PlaybackMoment {
    val id: PlaybackMomentId
    val journeyId: JourneyId
}
```

Suggested Version 1 types:

```kotlin
data class TitlePageMoment(...)
data class MemoryCardMoment(...)
data class StillPhotoPlaybackMoment(...)
data class LivePhotoPlaybackMoment(...)
data class ClosingPageMoment(...)
```

`PlaybackMomentId` may be:

* derived from a stored Moment ID for media;
* generated deterministically for title, Memory Card and closing pages.

Example:

```text
journey:{journeyId}:title
journey:{journeyId}:memory-card
moment:{momentId}
journey:{journeyId}:closing
```

These identifiers support deterministic playback testing without creating database rows.

# Playback Sequence

```kotlin
data class JourneySequence(
    val journeyId: JourneyId,
    val moments: List<PlaybackMoment>
)
```

Required order:

```text
Title Page
Memory Card
Stored Moment 1
Stored Moment 2
...
Stored Moment N
Closing Page
```

Rules:

* Title Page is always first.
* Memory Card follows the Title Page.
* Stored Moments follow `displayOrder`.
* Closing Page is always last.
* Missing files may be excluded or represented by recoverable placeholders.
* Sequence generation must be deterministic.

# Journey Status

Journeys require lifecycle state.

```kotlin
enum class JourneyStatus {
    DRAFT,
    IMPORTING,
    READY,
    FAILED,
    REMOVING
}
```

---

## DRAFT

Journey metadata exists but public playback is not ready.

Possible reasons:

* no media;
* import not started;
* story incomplete;
* cover not selected.

---

## IMPORTING

Import work is active or awaiting recovery.

A Journey in this state must not open through NFC during normal use.

---

## READY

Journey is valid for public playback.

Minimum requirements:

* unique valid slug;
* title;
* at least one playable stored Moment;
* resolvable local media;
* selected or automatically derived cover.

A blank story may be permitted technically, although the Workshop should strongly encourage completing it.

---

## FAILED

The most recent import or commit failed.

The owner may:

* retry;
* inspect the issue;
* remove the incomplete Journey.

Public playback must not open it.

---

## REMOVING

Deletion is in progress.

This state supports recovery if file cleanup is interrupted.

# Moment Entity Validation Rules

For `STILL_PHOTO`:

* `localStillPath` required;
* `localMotionPath` must be null;
* `motionDurationMs` must be null;
* `motionFileSizeBytes` must be null;
* pairing fields must be null.

For `LIVE_PHOTO`:

* `localStillPath` required;
* `localMotionPath` required;
* `motionDurationMs` required and greater than zero;
* `motionFileSizeBytes` required;
* pairing method required;
* pairing confidence required.

For all Moment types:

* width and height must be greater than zero;
* still file size must be non-negative;
* display order must be zero or greater;
* local references must remain within the app-managed Journey root.

SQLite cannot express every conditional rule cleanly.

Enforce them through:

* entity construction functions;
* repository validation;
* import verification;
* database tests.

---

# Moment Ordering

Moments are ordered within one Journey using `displayOrder`.

Recommended convention:

```text
0, 1, 2, 3...
```

Requirements:

* order unique within a Journey;
* order contiguous after a completed edit or import;
* drag-and-drop reordering updates all affected rows transactionally;
* sequence builder sorts by `displayOrder`, then stable ID only as a defensive fallback.

Do not use capture date as permanent display order.

The owner may arrange the story differently from chronological order.

---

# Reordering Strategy

For Version 1, rewriting contiguous integer positions is acceptable.

Example transaction:

1. validate that all supplied Moment IDs belong to the Journey;
2. validate no duplicates;
3. assign temporary negative or offset positions if required to avoid uniqueness conflicts;
4. write final contiguous positions;
5. update Journey `updatedAt`.

More complex fractional ordering is unnecessary for Version 1.

# Journey Resume State

Resume state is lightweight but may be persisted in Room because it refers to Journey and Moment identity.

```kotlin
@Entity(
    tableName = "journey_resume_states",
    foreignKeys = [
        ForeignKey(
            entity = JourneyEntity::class,
            parentColumns = ["id"],
            childColumns = ["journey_id"],
            onDelete = ForeignKey.CASCADE
        )
    ]
)
data class JourneyResumeStateEntity(
    @PrimaryKey
    @ColumnInfo(name = "journey_id")
    val journeyId: String,

    @ColumnInfo(name = "moment_id")
    val momentId: String?,

    @ColumnInfo(name = "playback_index")
    val playbackIndex: Int,

    @ColumnInfo(name = "saved_at")
    val savedAt: Long,

    @ColumnInfo(name = "completed")
    val completed: Boolean
)
```

`momentId` may be null when the current playback item is a generated page such as the Title Page.

The application may prefer storing a playback token rather than only an index.

A more stable model is:

```text
TITLE
MEMORY_CARD
MOMENT:{momentId}
CLOSING
```

Suggested field:

```kotlin
val playbackPositionKey: String
```

This is safer if Moment order changes after the resume state was recorded.

---

# Resume Rules

* Resume state is temporary.
* Reopening within the configured timeout may resume.
* Reopening after timeout starts at the Title Page.
* Completed Journeys clear or mark the state as completed.
* Removing a Journey cascades removal of its resume state.
* If the stored Moment no longer exists, restart at the Title Page.
* Resume behaviour must never prevent the owner from editing Moment order.

---

# Preferences Outside Room

The following should use DataStore rather than Room:

* default photo duration;
* title-page duration;
* Memory Card duration;
* Live Photo playback mode;
* Live Photo audio enabled;
* reduced-motion preference;
* instruction visibility;
* owner PIN configuration;
* resume timeout;
* idle screen schedule;
* evening brightness settings;
* physical-frame safe-area insets.

Journey and Moment records must not be stored in DataStore.

---

# Type Converters

Room may require converters for:

* `JourneyStatus`;
* `StoredMomentType`;
* `LivePhotoPairingMethod`;
* `PairingConfidence`;
* `ImportState`;
* `ImportStage`;
* ISO dates;
* epoch timestamps.

Prefer simple stable representations:

* enums stored as explicit strings;
* dates stored as ISO-8601 strings;
* instants stored as epoch milliseconds.

Storing enum ordinal values is discouraged because reordering enum constants can corrupt meaning.

---

# DAO Design

DAOs should remain focused and avoid returning mutable persistence entities directly to UI.

---

## JourneyDao

Suggested responsibilities:

```kotlin
@Dao
interface JourneyDao {

    @Query("""
        SELECT * FROM journeys
        WHERE status = 'READY'
        ORDER BY updated_at DESC
    """)
    fun observeReadyJourneys(): Flow<List<JourneyEntity>>

    @Query("""
        SELECT * FROM journeys
        WHERE id = :journeyId
        LIMIT 1
    """)
    suspend fun getById(journeyId: String): JourneyEntity?

    @Query("""
        SELECT * FROM journeys
        WHERE slug = :slug
          AND status = 'READY'
        LIMIT 1
    """)
    suspend fun getReadyBySlug(slug: String): JourneyEntity?

    @Insert(onConflict = OnConflictStrategy.ABORT)
    suspend fun insert(entity: JourneyEntity)

    @Update
    suspend fun update(entity: JourneyEntity)

    @Query("""
        UPDATE journeys
        SET status = :status,
            updated_at = :updatedAt
        WHERE id = :journeyId
    """)
    suspend fun updateStatus(
        journeyId: String,
        status: JourneyStatus,
        updatedAt: Long
    )

    @Delete
    suspend fun delete(entity: JourneyEntity)
}
```

## MomentDao

interface MomentDao {

Repositories coordinate Room and `JourneyStorage`.

# Repository Mapping

Persistence entities should map to domain models through dedicated mappers.

Example responsibilities:

```text
JourneyEntity + MomentEntity list
            ↓
JourneyMapper
            ↓
Journey domain model
```

Mapping should validate:

* slug;
* date consistency;
* Moment type requirements;
* file references;
* Journey ownership;
* ordering.

Invalid persisted content should produce a recoverable integrity result rather than an unchecked crash.

---

# Journey Aggregate Rules

Journey is the principal aggregate boundary.

Operations affecting Journey consistency should be coordinated through `JourneyRepository`.

Examples:

* create Journey;
* change slug;
* select cover;
* reorder Moments;
* mark ready;
* delete Journey.

Moment records should not be moved between Journeys through unrestricted DAO calls.

A future feature may explicitly support copying or moving a Moment.

It is outside Version 1.

---

# Journey Readiness Validation

Before changing a Journey to `READY`, validate:

* valid unique slug;
* non-empty title;
* valid date range;
* at least one stored Moment;
* each Moment passes type-specific validation;
* required local files exist;
* cover Moment exists or can be derived;
* all display orders are unique and contiguous;
* no active incomplete import owns the Journey.

Conceptual result:

```kotlin
sealed interface JourneyReadiness {
    data object Ready : JourneyReadiness
    data class NotReady(
        val issues: List<ReadinessIssue>
    ) : JourneyReadiness
}
```

---

# Cover Selection Rules

`coverMomentId` should normally reference:

* a Still Photo Moment;
* or the still component of a Live Photo Moment.

If no cover is selected:

1. choose the first valid Moment by display order;
2. derive its still reference;
3. optionally persist the selected Moment ID.

If the cover Moment is removed:

* automatically select the next valid Moment;
* or return Journey to Draft if no Moments remain.

---

# Duplicate Detection

Duplicate detection should operate at several levels.

---

## Duplicate Journey Candidate

Potential signals:

* same source folder name;
* same optional metadata slug;
* overlapping dates;
* matching source fingerprints;
* same title.

This should produce a warning, not an automatic destructive decision.

---

## Duplicate Moment Candidate

Potential signals:

* same source still fingerprint;
* same still file size and capture date;
* same motion fingerprint for Live Photos;
* same original file names within the same source folder.

The owner may choose to:

* skip duplicates;
* import anyway;
* inspect uncertain matches.

---

# Deletion Model

Deletion must be coordinated because Room and local media storage are separate systems.

---

## Remove One Moment

Recommended flow:

1. Confirm ownership and existence.
2. Mark or prepare deletion.
3. Delete app-managed still file.
4. Delete motion file when present.
5. Delete thumbnail.
6. Remove the Moment row in a Room transaction.
7. Compact remaining `displayOrder` values.
8. Update Journey `updatedAt`.
9. Repair cover selection if required.
10. Remove stale resume state when it points to the deleted Moment.

If file deletion partially fails:

* retain sufficient state for cleanup retry;
* do not silently lose the only database reference to an undeleted managed file.

A dedicated deletion journal may be introduced if testing shows it is required.

---

## Remove Journey

Recommended flow:

1. Require owner confirmation.
2. Set Journey status to `REMOVING`.
3. Stop any active playback of the Journey.
4. Delete app-managed Journey directory.
5. Delete Journey database row.
6. Allow foreign-key cascade to remove Moments and resume state.
7. Remove related completed import records according to retention policy.
8. Verify cleanup.
9. Never access or modify the original archive.

If file deletion fails:

* retain the Journey or cleanup record in a recoverable state;
* retry cleanup;
* do not report success prematurely.

---

# Database Transactions

Use Room transactions for:

* Journey and initial Moment insertion;
* Moment reordering;
* metadata update plus status transition;
* removal of rows after file cleanup;
* final import commit;
* cover repair after Moment deletion.

Room transactions cannot include file operations.

Application-level transaction strategies must coordinate both.

---

# Import Commit Model

A safe import should use temporary storage.

Suggested states:

```text
External source
      ↓
Import plan
      ↓
Temporary processed files
      ↓
Verification
      ↓
Room commit
      ↓
Final app-managed location
      ↓
Journey READY
```

The exact order of Room commit and final file promotion should be selected carefully.

One robust option is:

1. process files into a temporary Journey directory;
2. verify them;
3. promote the temporary directory atomically where the platform permits;
4. insert Journey and Moment rows in one Room transaction;
5. mark Journey ready;
6. clean up import tracking.

If database commit fails after promotion:

* remove the promoted local directory;
* retain the external source untouched.

If promotion is not atomic:

* track every file explicitly;
* make cleanup restart-safe.

---

# Import Failure Retention

Import failure records should retain only what is useful for recovery.

Potential retained values:

* stage;
* failure category;
* source folder display name;
* counts;
* timestamps;
* temporary workspace reference;
* retry eligibility.

Do not retain:

* sensitive file metadata unnecessarily;
* full source filenames in general logs;
* extracted GPS coordinates;
* image content in Room.

Old completed and failed import records may be cleaned after a configurable retention period.

---

# File Integrity

Each local media record may optionally store a checksum.

Possible purposes:

* verify successful copy;
* detect local corruption;
* support repair diagnostics.

A full checksum for every processed output is useful but adds import cost.

Recommended Version 1 approach:

* verify decoding after write;
* verify expected size is greater than zero;
* optionally calculate SHA-256 for final local media during import;
* store it only if corruption detection is implemented.

Do not add checksums without a consumer or maintenance plan.

---

# Referential Integrity

Required relationships:

```text
Journey 1 ────── * Moment

Journey 1 ────── 0..1 Resume State

Journey 1 ────── * Import Records
```

Rules:

* every Moment belongs to exactly one Journey;
* every resume state belongs to one Journey;
* an import may begin before Journey creation and therefore have a nullable Journey ID;
* deleting a Journey cascades Moment and resume rows;
* import history may be deleted or detached according to retention policy.

---

# NFC Association

The Journey slug is the NFC association in Version 1.

No separate NFC Tag entity is required for basic operation.

```text
NFC URI slug
      ↓
Journey.slug
```

A future `MagnetEntity` may be added if the product needs:

* multiple magnets for one Journey;
* tag serial tracking;
* lost-magnet management;
* tag-write history;
* custom physical magnet labels.

Version 1 should not store raw tag hardware IDs as the primary association.

Tag IDs may vary in availability and should not be required for playback.

---

# Slug Change Behaviour

Because the slug is written to physical tags:

* Workshop must clearly warn before changing it;
* changing the slug must not happen automatically when the title changes;
* the old tag will no longer resolve unless an alias is retained;
* Version 1 may require the owner to reprogram the magnet.

Optional future support:

```text
journey_slug_aliases
```

This is not required in Version 1.

To reduce accidental breakage:

* generate the slug during Journey creation;
* treat it as stable;
* hide advanced editing after the tag is written unless explicitly requested.

---

# Data Retention

Persist indefinitely unless the owner removes the content:

* Journey metadata;
* Moment metadata;
* local media references;
* owner-authored Memory Card text;
* ordering;
* playback preferences.

Temporary retention:

* resume state;
* import workspaces;
* import error details;
* diagnostic data.

Never persist by default:

* external-drive master files;
* unrestricted external folder access;
* GPS coordinates;
* cloud credentials;
* temporary decoder caches beyond normal cache policy.

---

# Privacy by Data Minimisation

The data model should retain only information required for the product.

Version 1 does not require:

* face recognition data;
* person labels;
* precise location coordinates;
* contact information;
* social sharing metadata;
* account identifiers;
* online analytics identifiers.

Capture dates may be retained because they help organise and understand Journey media.

GPS should be discarded unless a future owner-approved map feature is introduced.

---

# Database Versioning

The Room database must declare an explicit version from the beginning.

Example:

```kotlin
@Database(
    entities = [
        JourneyEntity::class,
        MomentEntity::class,
        JourneyImportEntity::class,
        JourneyResumeStateEntity::class
    ],
    version = 1,
    exportSchema = true
)
abstract class MagnetMemoriesDatabase : RoomDatabase()
```

Requirements:

* enable exported schemas;
* commit schema files to version control;
* test migrations;
* never use destructive migration in production;
* provide explicit migration paths.

During early development only, destructive migration may be used on disposable test builds.

It must be removed before real family Journeys are imported.

---

# Migration Principles

Migrations must preserve family content.

Priorities:

1. do not lose owner-authored stories;
2. do not orphan local media;
3. do not invalidate NFC slugs;
4. do not reset Moment order;
5. do not silently downgrade Live Photos into still images;
6. do not delete unknown future values without review.

Every migration should include:

* schema test;
* mapping test;
* representative Still Photo;
* representative Live Photo;
* Journey with optional fields;
* Journey with resume state.

---

# Enum Migration Safety

Enums should be persisted as stable string codes.

Example:

```text
still_photo
live_photo
```

Prefer explicit converters that do not depend on Kotlin enum names remaining unchanged.

Example:

```kotlin
enum class StoredMomentType(
    val persistedValue: String
) {
    STILL_PHOTO("still_photo"),
    LIVE_PHOTO("live_photo")
}
```

Unknown persisted values should produce a controlled integrity error.

---

# Date and Time Storage

Use:

* ISO-8601 strings for `LocalDate`;
* epoch milliseconds for `Instant`.

Journey dates represent local calendar dates and should not shift with time zone.

Capture timestamps may represent instants when metadata contains reliable timezone information.

When timezone information is absent:

* retain a local date-time representation carefully;
* or normalise according to a documented metadata policy;
* do not invent precision.

The media document should define exact metadata conversion rules.

---

# Database Backup Considerations

Version 1 playback is local-first, but the owner should eventually be able to back up the working journal.

A complete backup requires:

* Room database;
* app-managed Journey media;
* preferences;
* schema or manifest version.

The external 1 TB drive remains the master archive for originals.

The local database is still valuable because it contains:

* Memory Card stories;
* Moment order;
* captions;
* NFC slugs;
* cover selection.

These authored values must be included in any future backup/export feature.

---

# Portable Journey Manifest

Although Room is the active database, future-proofing benefits from a documented portable manifest.

A Journey export may eventually contain:

```text
journey.json
stills/
motion/
thumbnails/
```

The manifest may describe:

* Journey metadata;
* Memory Card;
* Moment order;
* media references;
* Live Photo pairs;
* schema version.

Version 1 does not have to implement full export.

However, the Room model should avoid values that cannot be represented in a documented manifest.

# Acceptance Criteria

The Version 1 data model is complete when:

* Journeys use stable internal IDs;
* NFC association uses a unique stable slug;
* Memory Card content is preserved as structured text;
* Still Photos and Live Photos are explicit typed Moments;
* Live Photo components remain one Journey Moment;
* Room stores metadata rather than media bytes;
* local media uses validated relative references;
* Moment order is deterministic and editable;
* imports have restart-safe lifecycle state;
* Journey readiness is explicitly validated;
* deletion never affects the master archive;
* resume state survives ordinary process recreation;
* database schemas are exported and migration-tested;
* one corrupted or missing Moment does not invalidate every other Journey record;
* the data can later be represented in a portable Journey manifest.

---

# Final Principle

> **The data model exists to preserve the family's stories safely, clearly and without tying them to one device, one cloud service or one moment in technology.**
